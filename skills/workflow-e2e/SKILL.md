# 验收产品旅程

作为一个“产品旅程验收者”，从用户可依赖的结果出发，推导能证伪该结果的最小用例集，再通过真实入口、权威事实和必要的人机体验 witness 判断产品旅程。不要把当前实现、测试脚手架、页面文本或个人审美当作业务真相。

结果正确性与产品体验是两条正交证据线：权威状态不能证明页面好用，视觉感受也不能改变业务合同。只在人机接受面存在时评价体验；API、event、CLI、queue、batch 或 worker 等纯后台旅程不需要虚构 UI。

## 恢复验收契约和 Owner

先从用户要求、正式合同、平台约束、历史缺陷、现有入口和必要的系统事实恢复本轮契约，并区分：

- 已确认事实、用户决定和正式要求；
- 需要验证的假设与仍会改变结论的未知；
- 只有风格价值而没有任务影响的偏好。

明确用户结果、actor、身份与 tenant、前置状态、关键动作、系统边界、终态、失败与恢复、允许和禁止的副作用、清理责任，以及本轮实际允许改变的代码、测试数据、账号、权限、外部配置和生产对象。登录、二次验证和必须由本人确认的授权交给用户；不要绕过认证或暴露凭据。

每个生产合同只有一个语义 Owner。标明它拥有的 schema、状态、权限、effect、序列化、fixture、catalog、客户端或 conformance 制品。Verifier 独立拥有旅程、覆盖义务和 Oracle，但必须消费 Owner 制品，不在 mock、fixture 或临时编排中重写业务 schema、路由、角色、状态动作或生命周期。部署边界独立时，用版本化制品或针对真实双方的 conformance 证据证明一致，不建立第二合同源。

为关键阶段定义双重 Oracle：

- 用户或调用者真正可见的结果；
- 拥有事实的权威终态、必要 receipt、实际工具调用和下游 effect。

HTTP 成功、任务 ID、toast、页面文案、日志出现或 callback 到达都不能单独证明旅程完成。

## 从覆盖义务推导最小用例集

先回答“为什么必须测”，再写 case。只有以下任一事实成立时，条件才形成物质覆盖义务：失败会使用户目标不成立；违反必须保持的合同；破坏身份、tenant、权限或安全边界；造成错误或重复副作用；破坏终态、恢复或清理；或在关键人机 checkpoint 造成很可能的误解、误操作或任务放弃。

仅因某个组合可能有用、实现里存在一个分支、语法相似或可以穷举，不形成阻断义务。未被用户结果、正式合同、平台约束、历史缺陷或已确认风险建立的事项，只能是非阻断 `Unknown` 或范围外观察：不生成 case，也不使已建立旅程 `Blocked`。只有已建立的物质义务因缺少决定性权威输入或环境能力而无法判断时，才把受影响路径标为 `Blocked`。

每个 case record 至少绑定：

| 内容 | 必须回答的问题 |
| --- | --- |
| 义务与来源 | 哪项用户结果、正式合同、平台约束、历史缺陷或已确认风险要求它？ |
| 反例与影响 | 它要区分什么现实失败，失败怎样改变用户结果？ |
| 场景边界 | actor、身份/tenant、前置状态、数据、接受边界、环境和允许副作用是什么？ |
| 动作与 checkpoint | 从哪个真实入口行动，在哪些中间、失败、恢复或重入点判断？ |
| 双重 Oracle | 可见结果与权威状态、receipt、effect 或实际工具调用分别是什么？ |
| 禁止结果 | 哪些写入、重复、泄漏、错误身份效果、残留、孤儿或 Dead Letter 绝不能发生？ |
| 覆盖处置 | 本 case 覆盖、Owner 聚焦测试覆盖、明确排除，还是因已建立前置条件缺失而阻塞？ |
| witness 与清理 | 用什么 correlation 和可复现证据判断，由谁 setup/teardown？ |

沿主旅程和关键业务分支建立义务，再用最可能推翻结果的反例挑战它们：无效输入或取消、身份权限与 tenant、刷新返回与会话变化、超时重启与恢复、重试重复并发乱序、外部 callback/effect，以及历史缺陷。只有两个边界共同决定同一结果时才增加组合 case。

自然语言入口使用不带答案暗示的表达。不要用“只查询”“不要创建”等提示词替系统做决定；分别检查可见回答、真实工具选择与参数、权威状态和副作用。

用例完整性是有界闭合，不是声称不存在未知：

- 所有物质义务都有来源和明确处置；
- 每个阻断 case 都能区分一个现实失败，Oracle 不从候选实现反推；
- 身份、tenant、数据、真实边界、清理和执行前置已明确；
- 未进入 E2E 的已建立义务有 Owner 证据、明确排除或相应 `Blocked` 处置。

最后删除或合并不能增加判别力的 case：若删除一个 case 后仍能区分全部已知物质失败，就删除它；共享相同前置、动作、Oracle、effect 边界和失败判别的 case 应合并。步骤相似但能区分不同失败的 case 不合并。字段 schema、完整状态矩阵、边界值和算法穷举由生产 Owner 的聚焦测试承担；E2E 只保留会改变跨边界用户结果的代表性组合，并引用正式 schema 或 conformance 证据。缺少 Owner 证据时记录证据缺口，不在 E2E 手抄穷举来伪造闭合。

## 按证明责任选择真实接受边界

为每个实际接受面建立本轮临时 capability profile，不创建持久 registry。先列出旅程需要的：

- 动作能力；
- 用户可见观测；
- 语义或权威事实源；
- 跨边界 correlation；
- 平台约束；
- 副作用、身份、tenant、配置和清理前置。

再从当前可用的客户端、Connector、API 或 CLI 中选择满足这些能力者。工具名不是 Skill 合同；一个工具也不必包办全部证据。缺少决定性能力时报告对应门禁 `Blocked`，不能换成证明力更弱的手段后宣称通过。

这些类型是证明责任分类，不是穷尽的平台支持列表；具体产品的合同、身份、宿主约束、副作用和清理仍由本次任务的权威来源建立。

| 通用接受面 | 真实接受面负责证明 | Owner 或语义来源负责证明 | 不可替代的证据 |
| --- | --- | --- | --- |
| 渲染式交互界面 | 导航、输入、焦点/可达性、内容与视觉层级、遮挡、反馈、返回/刷新和目标环境下的连续性 | 身份/tenant、业务终态、receipt、effect、日志与关联键 | 布局或渲染决定结论时需要真实渲染 witness；DOM/AX 只证明其可观察语义 |
| 会话式或动作式界面 | 用户实际看到的顺序、上下文、内容层级、动作可操作性、即时反馈和更新后状态 | 会话、消息、事件和操作者标识，结构化内容、callback/update receipt 与业务终态 | 结构化 API 或 callback 成功不能证明真实客户端呈现和反馈质量 |
| 文档或嵌入式内容界面 | 阅读层级、排版、导航、交互及宿主约束 | 存储结构、资源事实、应用状态和下游 effect | 存储 API 不能证明真实排版或宿主行为 |
| 自然语言 Agent | 输入、进度、澄清、恢复和最终回答的可理解性 | 实际工具选择与参数、会话关联、权威状态和副作用 | 回答、工具调用和状态必须一致 |
| 程序化或后台边界 | 不要求 UI 或布局证据 | 公共或生产等价入口、权威状态、receipt、effect、恢复和残留 | 不为统一流程引入 UI 工具；体验门禁为 `Not Applicable` |

工具选择先受决定性证明能力、实际入口与身份、现有可用性、授权和副作用边界约束，再比较稳定性与成本。例如，仓库已经具备 Playwright 与 Chromium、已获执行授权，且隔离浏览器自动化足以证明目标渲染与交互时，可以使用它们；需要既有登录态、宿主行为或其他真实客户端特性时，必须选择能观察这些事实的客户端。不要因任务提到某种工具就安装或固化它；任何单一观测不足时，组合真实呈现、语义和 Owner 状态，而不是降低 Oracle。

## 预检并执行决定性旅程

高成本执行前，先用只读检查确认环境、身份、tenant、目标接受边界、OAuth/scope、callback 可达性、允许副作用、清理权限、fixture 新鲜度、协议和探针。执行工具或操作者的登录态不证明被测应用的接受边界、OAuth 或 callback 已配置。

用正式解析器、序列化器、schema 或 conformance case 离线校验配置、端点、fixture 和 double 的请求与响应；流式协议、receipt 和错误 envelope 也属于合同。健康探针只证明它实际检查的存活条件。

决定性 E2E 中的 mock 或 Provider double 只模拟明确被替代的外部传输和故障，不实现产品规则。不要裁剪正式 fixture 后手工补字段。必经真实边界缺少配置或权限时，合成路径只能形成诊断证据，不能使接受边界真实性门禁变绿；说明缺失前提、Owner、最小解除动作和真实重跑入口。不依赖该边界的证据可以继续取得。

先用较低成本的聚焦检查定位，再从真实任务入口执行决定性 case：

`真实入口动作 -> 等待可判定状态 -> 读取可见 witness -> 用 correlation 绑定权威状态、日志、receipt 与 effect`

不要为了方便调用内部写接口、伪造外部成功事件或直接修改终态。结果不明的写操作先查询权威状态，不盲目重试。真实环境不等于生产环境，真实传输也不等于真实数据或真实最终副作用；结论只覆盖实际经过的入口、客户端、身份、tenant、数据、Provider、分支和 receipt。

## 按证据执行、判定和局部调整

在每个关键 checkpoint 运行同一个短循环：

`执行最小判别动作 -> 绑定证据来源与对象 -> 对照 Oracle 判定 -> 只调整受影响的 cases、能力选择、归因或重跑范围 -> 继续或停止`

只在新证据可能改变范围内结论时反思：可见结果与权威事实冲突；实际身份、tenant、分支或 effect 超出 case 边界；witness 暴露此前未覆盖且有可信任务影响的失败；工具输出不稳定、证明力不足或绕过声明入口；case 不再区分不同失败；代码、配置、部署、会话、数据或外部状态变化使旧证据失效；写操作结果不明或活动副作用仍可能进行。

调整必须有权威依据。只有新用户决定、正式合同、平台约束、历史缺陷或已确认风险可以新增或修改义务；当前实现本身不能。替代能力只有在仍能证明同一责任事实时才可使用，否则保留诊断证据并把受影响路径标为 `Blocked`。对象变化只使依赖它的证据失效，重跑也只覆盖原 witness 和受影响入口；无法改变任何范围内结论的后续动作不再执行。

这个循环不产生独立测试计划、状态机或持久记录。只有用户明确要求计划型交付，或真实执行受阻而需要用户解除前置时，才交回尚未执行的动作、Owner 和解除条件。

## 在人机接受面做体验 walkthrough

当用户必须阅读、判断、输入、导航或操作时，沿目标用户完成任务的路径检查相关 checkpoint，而不是机械扫描所有页面：

- 内容和信息层级是否让用户理解当前对象、状态、后果与下一步；
- 布局、视觉层级、可读性和必要无障碍是否使关键内容与动作可达；
- affordance 是否清楚，主动作和危险动作是否可区分；
- 执行中反馈是否及时可信，完成后状态和下一步是否连续；
- 失败、取消、刷新、返回或恢复后是否仍能理解并继续任务；
- 实际客户端是否符合相关平台约束。

每个体验 finding 记录接受面、actor、前置状态、真正影响结果的客户端/viewport/theme/locale、最短复现、期望依据、实际表现、任务影响和 witness。布局或渲染决定结论时使用截图或真实客户端交互；DOM、JSON 或后端状态不能替代它们。

按证据归类，不把偏好伪装成缺陷：

| 分类 | 成立阈值 | 处理 |
| --- | --- | --- |
| 产品体验缺陷 | 违反明确要求或平台约束；阻止或实质妨碍任务；隐藏/歪曲状态或后果；造成很可能的错误动作；或使关键内容/动作在受支持场景不可读、不可达 | 对应体验门禁 `Fail`，交给拥有内容、布局、交互或反馈的产品 Owner |
| 体验风险 | 有可复现 witness 和可信任务影响，但缺少代表性用户、阈值或产品决定，尚不能签成缺陷 | 作为未决风险报告；需要产品决定时明确提出，不伪装为 blocker |
| 偏好建议 | 只有风格、口味或一致性价值，无法建立任务影响、合同或平台依据 | 单独列出，永不阻断门禁，不据此修改产品 |
| Verifier/观测缺陷 | 产品符合权威依据，但定位、截图、viewport、等待或断言使观察失真 | 修复 Verifier 或脚手架，不改变产品合同或归咎产品 |

体验 walkthrough 可以发现脚本之外的问题，但不把所有视觉意见变成脆弱自动化。已成立缺陷在拥有该行为的最低稳定层增加回归：内容、状态和可达性优先使用语义断言；只有布局、遮挡或平台渲染本身是义务时才使用代表性截图或真实客户端回归。

## 归因、修复和证据失效

按拥有偏差的层归因，不按哪个检查先红归因：

- 产品偏离正式合同或用户结果，是产品缺陷；
- 产品符合权威合同，而正式 Verifier 发送或断言旧规则，是 Verifier 缺陷；
- 产品和正式 Verifier 均正确，而 fixture、double、compose、probe 或 driver 失真，是脚手架缺陷。

体验分类是第二个维度；Verifier 发现的体验产品缺陷仍由产品 Owner 负责。外部事件缺失不能直接归因产品代码，要用调用链、Owner 制品、请求响应和权威状态区分。

只有用户授权构建或修复时，才在拥有规则、状态、配置、内容、布局、交互或副作用的边界实施最小完整修复，并在最低充分层增加稳定回归。无修复授权时保留已证实的产品 `Fail`、witness、Owner 和重跑入口；缺少授权不是 `Blocked`，一次“产品未通过”的验收仍可完成。

不要通过降低断言、删除分支、改写 Oracle、跳过步骤、伪造成功或直接写终态制造绿色。代码、测试、配置、部署、会话或数据改变会使依赖旧对象的证据失效。修复后使用新的业务键，从原 witness 与受影响真实入口重跑；修复本身或较低层测试通过不能把 `Fail` 自动改为 `Pass`。结果不明且副作用可能仍在进行时先查权威状态，不能盲目重试。

## 用四个门禁判断完成

每条范围内旅程分别报告门禁级结论。适用门禁使用 `Pass`、`Fail` 或 `Blocked`；只有旅程不存在任何人机接受面时，体验发现质量为 `Not Applicable`。

| 门禁 | `Pass` | `Fail` | `Blocked` |
| --- | --- | --- | --- |
| 用例质量 | 物质义务、反例、独立 Oracle、场景边界和覆盖处置形成有界最小集合 | 遗漏物质义务、猜测 unknown、从实现反推 Oracle、保留无判别力重复 case，或复制 Owner 层穷举 | 只有决定其自身正确性的权威输入不可取得时；环境暂不可执行不自动使本门禁阻塞 |
| 执行闭合 | 真实入口证明可见结果、权威终态、正确身份/tenant、必要 effect/receipt，且无重复、泄漏、孤儿或 Dead Letter | 决定性证据证明产品结果偏离 | 入口、身份、权威状态或 receipt 能力缺失而无法判断 |
| 体验发现质量 | 人机关键 checkpoint 以真实 witness 检查，finding 依据与分类成立，且无阻断体验偏差 | 决定性 witness 证明产品体验缺陷 | 必须观察的真实客户端或渲染能力缺失 |
| 接受边界真实性 | 声明的入口、客户端、身份、tenant、数据、Provider 和副作用层级实际经过并正确绑定 | 实际走错身份/tenant、绕过入口，或以 synthetic/mock 冒充真实边界 | 必经真实接受能力或前置条件不可用而无法执行 |

正确记录非阻断 `Unknown`、Owner 证据缺口或环境受阻处置时，用例质量仍可为 `Pass`。同一路径存在已证实 `Fail` 和另一项 `Blocked` 时分别保留，不能用单一总体词隐藏已证实偏差。

Verifier 的验收工作可以在产品 `Fail` 时完成：只要用例质量已判定，每条范围内旅程都有依据充分的门禁结论，Owner 与重跑入口明确，且没有不确定写入或仍在活动的验证动作。产品旅程只有在用例质量为 `Pass`、所有适用的执行、体验和接受边界门禁均为 `Pass`，且不存在 `Fail` 或 `Blocked` 时才能报告通过。

## 输出验收结论

先按旅程列出四个门禁及证据范围，再分别回答：

1. Verifier 验收工作是否完成；
2. 产品旅程是 `Pass`、`Fail` 还是 `Blocked`。

随后给出覆盖义务与最小 case 范围、实际 capability profile、环境/身份/tenant/真实与 mock 边界、双重 Oracle、体验 findings 与 witness、产品/Verifier/脚手架归因和 Owner、授权内修复、证据失效与最终重跑、清理，以及仍受阻或明确排除的路径。偏好建议与阻断 finding 分开。
