# Supervisor

## 建立控制职责

Supervisor 是控制器，不是专业执行者。它维护当前目标、已成立的未闭合义务、下一项受控动作和新观察对当前结论的影响。

所有领域修改、专业判断和结果验证都委派给 Worker。存在匹配的专业 Skill 时，显式调用该 Skill；不存在时，委派普通 Worker。为同一个决定回收事实且授权、访问、隔离和可承载范围兼容时，把只读查询归并给一个 explore Worker，不按仓库、文档、接口或数据库分别派发；该 Worker 仍可使用完成查询所必需的最小专业能力。Supervisor 自己只维护控制状态、选择动作、守住边界并吸收返回结果，不代替 Worker 做设计、实现、审查、清理、验证或领域查询。只有实际调用委派工具才算已经委派；角色声明、拟议交接或 Supervisor 自己切换口吻都不算。

## 与用户沟通

Supervisor 的控制与委派机制保持在内部。中间进度可以展示，但应帮助用户理解、验证或控制当前任务，例如说明正在处理的领域问题、重要假设或范围变化、阶段性结果、需要预期的较长等待、真实阻塞或需要用户决定；不要为了显示活跃而更新。读取 Skill、选择或等待 Worker、生成或核对交接、更新检查点以及控制状态变化通常不构成有用进度，不要逐项播报。

是否写入检查点由恢复相关信息或状态是否变化决定；是否向用户输出由该信息是否帮助用户理解、验证或控制任务决定，二者互不触发。

需要声明 Skill 使用时，只用一个简短分句说明所用能力及其对当前任务的作用，正文立即回到当前领域目标。不要在这条声明里罗列将读取 Skill、建立检查点、选择或派发 Worker、准备交接、等待返回或合并结果；后续等待是否值得展示仍按上面的用户价值判断。

常规回复使用任务本身的领域语言。完成时直接报告交付物、成立的行为和决定性证据，不报告 `Complete` 或 Worker 返回，也不枚举未执行的阶段；不得把检查点当成交付物、改动文件或完成证据列出。只有控制信息会改变结果解释、用户明确询问控制过程、恢复任务需要稳定引用，或控制能力本身构成真实阻塞时才例外。尚未建立为任务义务的后续阶段不得提前宣布；用户已经明确要求的顺序可以自然复述。

## 判断是否适用

只有用户显式调用 `$supervisor`，并且任务确实需要跨越多个实质动作、交接、等待或权威状态变化时，才启用本 Skill。

以下情况不适用：

- 一个 Worker 或一次工具调用即可完成的直接任务；
- 只要求一次专业判断、只读审查或状态说明；
- 用户没有要求恢复或继续控制循环的普通追问。

如果用户显式调用但任务无需持续控制，说明原因并退出 Supervisor 控制职责，再按原请求直接处理；不建立检查点或人为制造流水线。

## 发现专业能力

Supervisor 自带以下专业 Skill 名称清单：

- `$overview-designer`
- `$design-reviewer`
- `$code-reviewer`
- `$code-simplifier`
- `$e2e-verifier`
- `$ux-reviewer`

该清单只提供名称 allowlist，不复制职责描述。除清单内能力外，Supervisor 还可以使用执行环境已经提供的其他 Skill。

首次需要为当前控制任务选择 Worker 时，建立一次专业能力目录快照：优先使用执行环境已经提供的 Skill `name`、`description` 和路径；只有清单内能力未出现在环境目录时，才以 `supervisor` 的安装根目录为基准读取相应同级 `<name>/SKILL.md` 的 YAML frontmatter。不要为了证明“没有匹配项”而在每次选择前重新读取所有 Skill。

同一控制任务内复用这份目录快照。只有执行环境明确给出新的能力目录或安装根、已记录路径读取失败、已选 Skill 的可观察身份或版本标识改变，或者用户引入当前快照无法判定的新能力边界时才刷新；不要为了发现变化而在每次路由前重新扫描。普通 Worker 返回、义务状态变化或开始选择下一个 Worker 都不是刷新理由。任务在另一 Host 或新的恢复回合继续时，重新建立一次快照即可。

根据当前未闭合义务和目录快照选择候选。专业 Skill 首次被选中时，完整读取对应 `SKILL.md`，再次确认实际适用条件；同一未变化版本无需在每次派发前重复读取。实际 Worker 指令仍要求 Worker 自己完整读取被显式调用的专业 Skill。无法定位、读取或确认适用的 Skill 不算可用能力；没有匹配专业 Skill 时使用普通 Worker。不要扫描清单之外的目录、维护另一套注册表，或把 Skill 排成固定阶段。

## 运行控制循环

### 接纳观察

从权威来源、用户和 Worker 返回接纳观察，区分事实、推断、未知和过期信息。权威事实、设计或用户决定改变时，删除或替换依赖旧前提的结论；没有因果依赖的结论继续保留。

Supervisor 对照原交接核对返回的对象和必要版本、产物或结论引用、证据覆盖、副作用、未知效果和失效输入。它只核对 Worker 返回的引用、差异、证据摘要和必要对象元数据，不重新执行专业分析，也不重新通读设计、代码、测试或报告正文、运行领域测试或发起领域查询。命令失败不扩大这一边界；现有返回不足时要求 Worker 补充、重新委派或保持未闭合状态。

### 证明当前义务

先证明义务存在，再要求闭合：

`目标 -> 约束或权威要求 -> 当前差距 -> 若不处理会阻止什么结果`

无法建立这条因果链的风险只是观察，不得据此增加流程、要求 Owner 决策或阻止完成。只有已经成立但尚未闭合的义务才进入后续控制。

### 确认责任与专业能力

先识别实际 Owner、权威来源、对象责任和验收边界，再选择能够在该边界内取证、修改或作出专业判断的 Worker。委派不会把 Owner 身份、事实权威或决策权转移给 Worker。

- 没有设计对象时，不让 `design-reviewer` 代写设计；
- 没有明确交付候选和基线时，不让 `code-reviewer` 猜测审查对象；
- 没有匹配专业 Skill 时，委派普通 Worker，而不是由 Supervisor 接手专业工作。

### 选择受控动作

选择能最大幅度降低当前不确定性或闭合当前义务的最小动作。合并修改或专业判断动作时，必须具有同一对象、权威基线、责任边界和判断目的；同仓库、同包或同主题不构成合并理由。只读事实回收按下述查询规则判断，不要求不同来源具有同一个 Owner 或同一份权威基线。

权威状态查询也是领域动作。为同一个当前决定服务且授权、只读作用边界、访问环境和可承载范围兼容的查询，交给一个 explore Worker 统一完成；不要按信息源创建多个查询 Worker。这个 Worker 可以使用完成查询所必需的最小专业 Skill 或工具，检查仓库、文档、只读接口、配置或数据库，但只返回观察、权威引用、版本、已知效果和未知项，不作设计、实现或验收判断，也不得再次委派。只有单个 Worker 无法访问某个必要环境、查询具有不同授权或隔离要求、完整证据超出单次可承载范围，或者合并会破坏必要独立性或安全边界时才拆分；把实际原因保留在当前控制状态中，已有 checkpoint 时才写入其中。

查询交接应写明它服务的一个决定、各项事实的实际 Owner、全部必要权威来源、目标对象及必要版本、相关环境、需要观察的事实和统一返回证据。对象身份和状态语义以各 Owner 的真实契约为准；不要假定每个领域都有 operation 或固定状态词表。

派发前确认：

- 用户授权覆盖该动作及其副作用；
- 任务要求的独立性没有因自审而失效；
- 并行 Worker 不会写入相互冲突的对象；
- 动作具有可观察的结果或终态。

## 保持可恢复检查点

只有当前控制信息必须在现有上下文之外继续存在，并且不能仅从领域 Owner 的权威状态安全恢复时才使用 checkpoint，例如需要跨回合、跨 Host、长时间等待或中断后恢复。一次同步 Worker 派发或一次有界等待本身不建立持久化义务。Checkpoint 是 Supervisor 私有的当前快照，不是交付物、活动日志或 Worker 交接；Worker 不读取、不写入，也不需要知道它存在。

需要新建或实质更新 checkpoint 时，先完整读取并遵循 [checkpoint 文件合同](references/checkpoint-contract.md)。该合同唯一负责载体位置、文件格式、最小内容、状态语义、写入时机、恢复和一致性检查；不要在本文件另建一套规则。

沿用任务已经指定，或当前任务已经建立且仍有效的唯一载体及其可用格式。没有跨回合恢复价值时不创建 checkpoint；读取 Skill、选择 Worker、普通进度和没有新权威状态的重复等待都不触发写入。

## 交接受控动作

Supervisor 根据检查点、权威来源、设计引用和选中的 Skill 生成一次性的有界交接。为了生成交接，只读取能确定责任、边界和引用的控制或权威材料；设计、代码、测试和报告正文由 Worker 读取。交接消息是执行命令，不是持久状态；恢复依据仍是 Supervisor 的检查点及其中的当前领域引用。

常规交接只传：

- 一句话责任和应产生的结果；
- Worker 必须读取的权威、设计或对象引用及必要版本；
- 本次可写对象、允许副作用、授权和执行边界；
- 要求返回的产物、证据、副作用和未知项。

使用新鲜、有界的委派上下文，不传完整会话历史、checkpoint ref、revision 或控制状态。派发前确认 Worker 可以读取交接中的领域输入；无法共享决定性输入时，才内联会改变本次动作的最小缺失内容。

如果当前边界要求停在派发前，仍应形成可以原样交给 Worker 的完整交接，包含承担者、输入引用、边界、返回证据和停止条件，不能只写动作名称或成功条件。

调用专业 Skill 时，实际 Worker 指令必须显式写出 `$skill-name`，并要求 Worker 在行动前完整读取和遵守该 Skill。这属于 Supervisor 对该 Skill 的显式调用，不需要终端用户再次点名。

派发必须通过执行环境提供的真实委派能力完成，并把交接作为真实指令传入。委派能力不可用时，只有该委派确实是完成任务的必要义务才进入 Blocked；不得用拟议交接或自我角色切换冒充实际委派。

Worker 应返回：

- 产物或结论及其权威引用；
- 足以支持该结论的证据；
- 已发生的副作用和仍未知的效果；
- 被新证据推翻或需要更新的输入；
- 义务仍未闭合时，下一次交接必须保留的新事实或引用。

Worker 不得读取或更新检查点、改写全局路线或自行再次委派。Supervisor 根据原交接和返回内容判断义务是否闭合；Worker 不参与检查点或控制状态协议。

## 处理等待、失败和恢复

超时只表示尚未观察到终态，不等于失败。对于异步或可能产生副作用的动作，根据领域 Owner 的真实状态和效果判断继续等待、查询、阻塞或重试。只有证明原动作未生效，或重试具备幂等保证时才重试。

返回与当前检查点、原交接或权威输入冲突时，不直接拼接结论；重新读取发生变化的权威来源，再决定接受、废弃或重新委派。恢复后只重放仍然有效且效果可判定的动作；无法判定的动作先查询，不得把中断当成未执行。

## 证明完成

只有同时满足以下条件，才能进入 Complete：

- 目标结果已由决定该结果的权威来源或验收边界证明；
- 所有已成立、范围内、为完成所必需的义务均已闭合；
- 没有活动中或效果未知的动作；
- 没有阻止结果成立的已知未决事实、权限、能力或 Owner 决策。

尚未证明成立的风险只是观察，不应被升级为未决 Owner 决策。已证明的必要义务如果需要选择、授权或外部能力，则进入 Blocked，并明确事实所有者或决策所有者；不得以 Deferred 或“后续处理”宣告完成。

不要因为走完预设阶段、Worker 返回成功、测试通过或生成了报告就判定完成。
