# Checkpoint 文件合同

本合同只在 Supervisor 已确认当前控制信息必须在现有上下文之外继续存在、且不能仅从领域 Owner 的权威状态安全恢复时加载。Checkpoint 是 Supervisor 私有的当前控制快照，不是产品设计、任务报告、活动日志、证据库或被委派执行者的交接材料。

## 选择唯一载体

按以下优先级选择唯一载体：

1. 用户、任务或执行环境已经指定，或当前任务已经建立且仍有效的 checkpoint 文件；
2. 当前任务存在属于交付 Owner、可写的项目根目录时，使用该项目下 `.supervisor/<task-id>.md`；
3. 没有适用的项目根目录时，使用操作系统临时目录中的任务专属子目录及 `checkpoint.md`。

多仓任务选择拥有当前交付物或主要副作用的项目根，而不是机械使用当前工作目录。Task id 优先使用用户、任务或执行环境提供的稳定标识；都没有时，使用可识别任务的短名称加随机 UUID 或等价的抗冲突后缀，并在后续恢复中沿用同一名称。

不得另建平行 checkpoint，也不得写入执行框架（harness）或其它工具拥有的全局状态、配置、缓存、日志、可视化、记忆或安装目录，也不得写入仅因可写而选中的其他产品目录。项目内 checkpoint 是运行产物，不得被 stage、commit 或放入 MR；不得为了它修改项目或 Git 配置。若当前执行边界无法保证它不进入产品提交，则该项目载体不适用，使用临时目录。

项目目录必须实际拥有当前交付物或主要副作用；不得为了获得稳定路径而选用无关仓库。临时目录只保证当前运行实例和目录生命周期内的恢复，使用时在 checkpoint 中写明这一限制。项目根存在时不要仅因为临时目录足以覆盖当前等待就改用临时目录；但仍不得仅为同步委派创建 checkpoint。

## 文件格式

沿用已有载体的可用格式，只有现有表示妨碍恢复判断时才调整。新建文件默认使用真正的 Markdown；不得把裸 YAML 写入 `.md`。只有环境提供机器消费者、固定 schema 和校验器时才使用 `.yaml`，并按该 schema 校验。

新建 Markdown 可以从以下最小结构开始，并删除当前状态不需要的章节：

```markdown
# <可识别当前任务的 checkpoint 标题>

- Task: `<stable task reference>`
- State: `Active | Waiting | Blocked | Complete`
- Revision: `<only when stale snapshots must be distinguished>`
- Recovery boundary: `<project/runtime/temp lifetime when material>`

## Result and acceptance boundary

<目标结果以及决定它是否成立的边界。>

## Authorization and preserved behavior

- Allowed: <已授权作用>
- Forbidden: <禁止作用>
- Preserve: <必须保持的行为>

## Governing references

- <权威、设计或对象引用及必要版本>

## Open obligations

- [ ] <已证明成立的未闭合义务及其因果依据>

## Current action

- Owner: <被委派执行者或真实领域 Owner>
- Inputs: <有界引用>
- Effect boundary: <允许作用与副作用>
- Expected result: <可观察结果>
- Stop condition: <停止或重入条件>

## Active or unknown effects

- <仅 Waiting 或效果未知时保留>

## Valid conclusions and evidence

- <仍决定下一动作或完成判断的结论及引用>
```

这是可调整模板，不要求逐字使用标题或字段名；要求是 Markdown 格式与下述控制语义成立。

## 当前快照内容

只保留删除后会改变下一动作、恢复判断或完成判定的信息：

- 目标结果、验收边界、授权、禁止效果和必须保持行为；
- 直接决定当前路线的权威、设计和对象引用，以及可变对象的必要版本；
- 当前状态、所有已成立且完成前必须闭合的义务，以及当前选中的义务；
- 仍影响下一动作、恢复或完成判断的结论和证据引用。

用稳定、可读取的引用代替正文复制。设计决定当前路线时记录 `design ref`；设计可变时附可区分当前依据的版本。Complete 指向已验收产物及其 revision、commit 或 diff 依据，不用文件大小、行数或修改时间标识版本。

不要求通用 action ID、runtime ref 或执行者身份协议。领域 Owner 提供恢复查询必需的稳定标识时，把它作为领域对象引用。

## 状态语义

- `Active`：没有已接受但结果未知的动作。下一动作通过 Guard 后，记录责任、输入引用、作用边界、预期结果和停止条件，但不得提前声称已经派发。
- `Waiting`：动作已被接受但尚未返回。记录可能发生的效果、权威反馈来源、预期证据和安全重入条件。
- `Blocked`：已成立义务缺少事实、权限、能力或决策。记录实际 Owner 和最小解除条件；`Needs Authority`、`Needs Input` 是原因，不是新状态。
- `Complete`：决定性结果已有权威证据，所有范围内义务闭合，没有活动或效果未知动作，并且该 checkpoint 不可继续恢复。

不得用 `Deferred` 隐藏未闭合义务。

## 写入与恢复

只在恢复相关信息或状态变化时写入：

1. 接纳会改变决定的事实、义务、权威引用或路线后，在执行依赖它们的动作前更新；
2. 派发前写入 `Active` 的动作依据、责任、边界、预期结果和停止条件；
3. 派发被接受且尚未返回时，在等待前更新为 `Waiting`；
4. 返回、超时、失败或效果未知时，先对照原责任核对反馈并确定受支持的状态，再更新，之后才能重试或选择下一动作；
5. 交还控制或进入 `Blocked` 前更新；完成时按下述退出规则处理载体。

优先使用载体自身的版本；只有需要区分陈旧快照时才维护 revision。没有新权威状态的重复等待、轮询、普通进度、能力读取和内部路由不触发写入。

如果动作可能已经产生效果，但对应 `Waiting` 尚未落盘就发生中断，恢复时把效果视为未知，不得依据旧 `Active` 直接重试。恢复后先读取 checkpoint，再刷新可能变化的权威来源。

只有等待、阻塞或以后恢复确实需要用户持有稳定引用时，才报告 checkpoint ref、版本、状态、下一动作或重入条件。交还仍为 `Active` 的恢复任务时，面向用户说明下一动作；完成时只报告领域结果和证据，不把 checkpoint 当成交付物或完成证据。

## 完成后的退出

完成判定成立后，不留下无 Owner、无消费者、无删除条件的运行文件：

- 用户、任务或执行环境指定的既有载体，按其 Owner 的保留规则写成 `Complete`；规则未知时保留载体，不擅自删除，并在载体中标明不可继续恢复；
- Supervisor 新建的临时或项目 checkpoint，如果没有已建立的保留义务，在最终回复前删除；删除前必须已经从权威来源证明完成，并确认没有活动或效果未知动作；
- 已建立保留义务时，写成 `Complete`，记录保留 Owner 和删除触发条件。Checkpoint 不能因“可能以后有用”无限期保留。

## 写入前检查

- 只有一个当前状态，并且状态、当前动作和活动效果一致；
- 每个开放义务都能建立“目标 → 权威要求或约束 → 当前差距 → 阻止的结果”的因果链；
- 用户决定、权威版本或对象状态改变后，依赖旧前提的动作、阻塞、结论和证据已经删除或替换；
- 不同时保留“尚未发生”和“已经完成”的同一事实；
- `Complete` 没有开放义务、活动动作或未知效果；
- 不保存秘密、完整提示词、能力描述或目录、被委派执行者的对话、旧候选、活动历史或未证明的未来阶段；
- 文件位置仍属于当前任务的恢复边界，并且不会进入产品提交。
