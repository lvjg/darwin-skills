# 控制系统级交付闭环

## 建立控制契约

`plan-to-delivery` 定义系统级交付从原始意图到最终证据的控制方法。只有意图准入成立后，执行本 Skill 的 agent 才承担 Controller 角色；准入前只判断当前请求是否需要这种控制方法。设计、评审、实施、验收和清理由相应专业 Worker 负责。Controller 直接运用模型已有的长程推理和推进能力，不另建固定状态机。

Controller 持续维护四项控制事实：原始结果与授权、当前权威对象及版本、闭合责任方、有效证据与未闭合条件。每轮先从检查点及其权威引用恢复这些事实，再定位当前缺口、受影响对象与闭合责任方，最后选择通过 Guard 的最小充分动作。检查点记录当前控制状态，交接传递独立判断所需上下文，接纳决定哪些观察可以改变控制状态，路由把每个缺口交给其闭合责任方，完成判断以最终对象和结果证据为准。

“权限方”指有权改变目标、范围、授权、风险容忍、不可逆选择或设计采纳的用户或其他授权主体；“闭合责任方”描述当前缺口由谁关闭，可由权限方或有权查明事实、修改对象、作出专业判断或恢复执行的 Worker 承担；设计和评审讨论的业务或技术归属称为“系统责任边界”，不能直接决定下一 Worker。

在会采纳或替换权威对象、启动新的共享或外部副作用、使后果难以撤回，或完成交付的关键边界，Controller 不得只沿用检查点。设计采纳、开始实施、Controller 恢复或转移以及最终完成前，沿检查点引用重新读取权威来源，重建四项控制事实并与当前快照比较。发现差异、来源不可读或无法证明新鲜时，使受影响结论失效并停止依赖动作，再把事实或专业判断缺口交给相应闭合责任方，把权限缺口交给权限方；不得用旧摘要或模型记忆补全。

Controller 按以下关系维护权威对象和门禁：

- 权限方对当前可定位的设计候选进行采纳，使它成为已采纳权威设计；
- Plan Reviewer 独立判断该设计是否足以支持“开始实施”这一具体决策，评审结论不改变采纳状态；
- 只有设计已采纳且有效 Plan Review 结论支持开始实施时，才能进入实施；实现候选经 Delivery Review 成为已验收候选；
- Cleanup 没有改变候选时可以复用原验收；产生实质变化时，使依赖该变化的旧结论失效，由相应闭合责任方完成必要复核，并由 Delivery Reviewer 对最终相关快照重新判断。

每个对象、门禁和结论都必须能追溯到精确来源、版本与证据。任务检查点只索引这些权威对象，不取代它们。

只有权限方能建立或改变根目标、范围、风险容忍、授权、不可逆选择和设计采纳。权威事实约束可行性与必须保持的现状，但不能修改或缩减根目标。已采纳设计和对象匹配的新鲜专业结论只在各自责任范围内约束后续工作。Controller 推断在验证前保持为假设；Worker 提案在接纳前不能成为需求、完成标准、采纳依据或权威事实。

Controller 持续把用户可观察的业务或系统结果作为原始结果不变量，并区分：

- **结果义务**：直接证明原始结果、质量门槛和必须保持的行为；
- **必要闭合**：当前责任边界达成结果所需的最小支撑变化，且有判别证据证明当前路径或更小路线不能满足同一门禁；
- **独立目标**：增加原任务不要求的结果承诺、责任、权威、受影响系统、生命周期或长期负担，只能由相应权限方明确接纳。

局部机制、测试、产物、健康或治理证据只能证明对应事实，不能替代结果义务。新发现默认不扩大范围。

Controller 可以理解完整技术内容、综合和质疑交回、拒绝接纳无效主张，并判断受影响对象与闭合责任方；不得在当前上下文中创建设计、代码、专业评审、交付验收或清理产物，也不得代签专业结论。约束的是专业判断和副作用的归属，不是 Controller 的认知能力。

Controller 按权威对象确定闭合责任方：

- 权限方：处理根目标、范围、风险、权限、设计采纳和不可逆选择；
- Design Worker：使用 `$system-overview-design` 创建或修订目标设计候选，并闭合 Plan Review 对候选设计的有效 finding；
- Plan Reviewer：使用 `$plan-review` 独立判断当前可定位的完整设计是否足以支持开始实施；设计采纳与该专业判断是两个独立门禁，实施前必须同时成立；
- Implementation Worker：依据已采纳且有效 Plan Review 结论支持实施的完整设计形成候选，并修复 Delivery Review 发现的实现缺陷；
- Delivery Reviewer：使用 `$delivery-review` 对当前可定位候选，结合接受意图、授权边界、完整设计、实际交付面和门禁证据，独立判断它是否满足明确的下一 Gate；
- Cleanup Worker：使用 `$code-cleanup` 清理已验收候选，并修复由清理引入的缺陷；
- Evidence Worker：从决定事实的来源补充有界证据，不修改被评估的专业对象或代签专业结论；
- Controller：绑定语义、对象和新鲜度，路由责任，并恢复 Worker、工具、会话、通信或执行环境故障；这类执行故障不自动成为目标系统的设计问题；
- 任务特定通用 Worker：承担已经明确但没有专用 Skill 的责任。事实来源或责任未知时，先做有界只读责任发现；权威在授权之外时停在外部 blocker 或用户 Gate。

`plan-to-delivery` 只定义控制方法，各专业 Skill 只提供本领域方法；它们都不拥有用户目标、权威事实或产物，上述角色也不是封闭责任集合。Reviewer 的路由建议只是提案；责任不能由 Skill 名称、调用顺序或 finding 出现的阶段决定。

Controller 必须保持以下执行不变量：作者不得评审自己创作的同版本产物；专业结论绑定精确对象和证据范围；共享工作区同一时刻只允许一个写入 Worker，除非依赖、写入面和门禁已被证明互相独立；没有通过目标、授权、角色、对象、写入和证据检查的动作不得执行；没有最终快照的结果证据不得完成。

## 判定意图并建立当前状态

显式调用本 Skill 只触发准入判断，不自动建立 Controller、Goal、检查点或 Worker。先读取当前请求及其明确引用的上下文，用自然语言重建本轮结果、交付物、范围、授权、完成标准和下一决策，再判断两个条件：

1. **控制意图**：用户要求本 Skill 控制工作如何从当前状态推进到最终交付；
2. **控制必要性**：存在与当前意图匹配的活动检查点，或当前结果确实需要持续对齐系统级目标设计、实施候选、独立专业判断和最终结果证据。

先判断控制意图。Skill 名称、链接、调用标签、任务时长、文件数量、验证、外部写入、提交或发布都不能单独证明它成立。若不成立，不建立控制状态，直接按当前请求的实际语义继续；除非这会改变用户预期、权限或可完成性，否则不单独汇报准入过程。

控制意图成立后，才按权威优先级恢复能决定控制必要性的事实：

1. 当前任务或上层上下文明示已绑定 Goal，或用户明确要求创建、设置或使用 Goal 时，调用 `get_goal`。匹配的活动 Goal 成为稳定根目标来源；冲突时停在用户 Gate。没有这些信号时不调用 `get_goal`。
2. 查找当前任务或可信交接中的活动检查点。沿其引用重新读取根目标来源、当前权威对象和关键证据，再用当前用户意图及匹配 Goal 核对对象、结论、活动 Worker、副作用和未闭合条件。匹配时接纳为恢复基线；即使只剩一个有界的验收、修复或清理动作也属于续跑。若一个声称属于当前根目标或共享写入面的活动检查点与当前意图冲突、来源不可读或无法证明新鲜，将其视为恢复 blocker；若当前任务、可信交接、活动 Worker、未收敛副作用或权威产物表明此前存在活动 Controller，且按本 Skill 应已留下持久检查点，但预期检查点缺失或不可读，也作相同处理。在确认原 Controller 已终止、检查点已失效或用户完成 Controller 转移前，不得建立新闭环。
3. 只有没有证据表明活动检查点应当存在时，才读取相关会话与决定、引用文档、已有设计，以及决定当前事实所必需的来源，补全结果与交付物、范围与非目标、完成标准、必须保持的行为、授权和会改变路线的未知。
4. 只做足以判定入口并界定 Design Worker 探索边界的最小只读检查：定位已有设计及状态、事实来源、可能受影响的系统或责任边界，以及专业探索应继续读取和明确排除的范围。信息足以判断准入或形成首轮交接时停止；不要在入口调查中重建完整系统模型、选择技术路线、定义合同、状态或恢复机制，也不要派发 Design Worker 来判断是否需要 Design Worker。

控制必要性成立时，有匹配检查点则恢复 Controller，确认不存在相关活动检查点时才建立新闭环；存在恢复 blocker 时停在恢复，不建立 Controller 或派发 Worker。匹配检查点只剩一个有界的验收、修复或清理动作时，仍属于续跑。控制必要性不成立时，不为适配流程制造设计或阶段；不建立控制状态，直接使用普通工作方式或匹配的单一专业 Skill 继续当前请求。

Controller 只在入口成立后建立控制基线和任务检查点。基线绑定原始请求与后续决定的精确来源、结果与交付物、范围和非目标、必须保持的行为、完成与停止条件、已授权副作用、待用户决定的选择，以及仍会改变路线的未知及其来源状态。

Controller 把 Goal 视为可选的持久目标契约，而不是工作流运行时：

- 不因任务较长、多阶段或使用本 Skill 而创建 Goal；
- 只有用户或更高层明确要求创建、设置或使用 Goal，且先前 `get_goal` 未找到匹配活动 Goal 时，才调用 `create_goal`；目标必须含具体结果、范围、最终证据标准和停止条件，只在用户明确要求时设置 token budget；
- Goal 只保存稳定根目标、范围和最终证据，不承担阶段、路由、finding 接纳、纠偏、检查点或日志；Worker 不更新 Goal；
- 任何 Goal 更新前重新核对它，只在本 Skill 的完成条件全部成立时完成 Goal。

Controller 维护一个自然 Markdown 的逻辑任务检查点，只保存当前控制快照：

- **检查点身份**：对应任务、当前 Controller、权威载体及这份快照是否仍为活动权威的可定位引用；
- **根目标绑定**：意图与决定的精确来源、已接纳解释、范围、非目标、授权、必须保持的行为、完成与停止条件；
- **权威对象**：当前设计候选或已采纳设计的精确版本、设计门禁依据、实现或最终候选，仍有效专业结论的对象、范围和新鲜度，以及已取得和仍缺少的结果证据；
- **活动执行**：活动 Worker、共享写入面、已知副作用、等待条件及其可定位状态；
- **待闭合控制**：会改变下一动作或完成判断的条件、受影响对象、闭合责任方、待验证未知及其来源状态、所需证据或决定，以及下一动作候选、依据和失效条件。

所有进入本 Skill 的任务都维护逻辑检查点，但不是都要持久化。Controller 把它维护成当前快照，不追加为日志、固定阶段状态、任务图、接受台账或完整历史。只有 Controller 可以更新它；在接纳观察、派发或结束 Worker、用户决定、授权或权威对象变化后刷新。原始交回未经接纳不得进入检查点；未接纳主张、已解决 finding、后续义务和范围外观察也不进入。对象、配置、数据、环境或证据变化时，只替换失效引用和依赖结论。

恢复边界不是任意回合结束，而是 Controller 转移，或 Controller 交出控制权时任务仍有或即将产生可能跨回合运行的 Worker、未收敛副作用或共享写入、不能仅沿权威引用有界重建的控制事实。不要依赖无法预测的自动上下文压缩或压缩前回调；在派发可能跨回合运行的 Worker、发起本轮结束时可能仍未收敛的副作用、进入等待、结束任务仍未完成的回复或转移 Controller 前，检查是否会创建或跨越恢复边界。首次创建或跨越该边界前建立持久检查点；此后任务未完成期间，每次控制事实变化都覆盖当前快照，并在再次跨越边界前确认它可读。没有上述状态且事实均可从权威来源有界重建时，逻辑检查点已经足够；纯只读调查或只为选择持久载体而请求权限方决定，可以结束当前回合而不先持久化。

持久载体按以下顺序选择：当前环境由工具契约或已验证恢复行为明确保证跨上下文压缩和任务恢复可读的任务级状态、已有且可信的任务级持久交接载体、用户授权并指定位置的独立任务级 Markdown。工具或界面把内容称为 `plan`，不足以证明其持久性。不要把检查点写入 Goal、`system-overview-design` 产物或默认写入产品仓库，也不要创建独立 Playbook。若没有经过确认的持久载体，Controller 不得创建或留下需要跨恢复边界保存的状态；仍可继续能在当前连续执行内完成或可从权威来源有界重建的工作，并可在没有活动 Worker、未收敛副作用或共享写入时，以明确的 best-effort 限制请求权限方选择载体。无法先收敛这些状态而又必须跨越恢复边界时，报告能力 blocker。

任一时刻只允许一个活动 Controller 和一个权威检查点。投影或切换载体时，先写入并重新读取新快照，再把它声明为权威检查点并撤销旧载体的活动权威；旧载体不能更新时，由同一可信交接明确它已被替代。其余副本只用于读取，不得独立更新。只有用户能转移 Controller；原 Controller 先停止派发并保存检查点，接收方读取后核对活动 Worker、副作用和未闭合条件，再接管并切换权威状态。

## 运行单轮控制闭环

Controller 重复执行：

`恢复当前锚点 -> 接纳观察并刷新检查点 -> 定位受影响对象与闭合责任方 -> 选择最小充分动作 -> 通过 Guard -> 派发并记录活动 Worker 或等待 -> 接收交回 -> 回到接纳`

每个 Worker 交回都只是下一轮的观察、证据或转换提案，不能直接改变权威控制状态。

### 接纳观察并定位责任

Controller 直接读取 Worker 声称的产物与证据，并核对：

1. 是否绑定正确根目标、精确受托对象和当前有效版本；
2. 事实是否来自决定它的源码、数据、运行环境、活动合同或其他权威来源；
3. 是否与已采纳设计、必须保持的行为和仍有效结论一致；
4. 是否在授权和受托范围内，且没有把推断或提案冒充用户要求；
5. 是否足以改变当前门禁、未闭合条件或下一动作。

Controller 只作控制接纳，不补写专业产物或代签专业判断。Design Worker 声称 `Confirmed` 仍是提案；只有权限方对当前精确路线和关键机制的可定位决定才构成设计采纳。要求交付结果、授权写入或要求继续，不自动采纳 Worker 后来加入的机制、保证或验收门槛。

上下文隔离可以降低作者锚定和自证偏误，但不能生成新事实或消除共享能力边界带来的共同盲区。多个同类 Worker 的一致意见不得把模型推断升级为事实；能由权威来源、测试、运行查询或探针判定的事实前提，先取得判别证据。基于这些事实仍需专业判断的内容，保持为绑定对象、范围和依据的专业结论；仍会实质改变用户风险容忍、授权或不可逆选择的不确定性，进入用户或相应权限方 Gate。

finding 只有建立以下因果链，才可进入检查点并驱动闭环：

`根目标或必须保持的行为 -> 实际受影响对象及系统关系 -> 当前门禁的可观察差异 -> 决定事实的来源 -> 闭合责任方与最小闭合条件`

未建立该链时，按实际性质处理：

- 可能改变门禁但事实缺失或过期：证据缺口，只派发有界补证；
- 当前门禁不需要但以后可能有价值：后续义务；
- 会改变目标、范围、风险、授权或不可逆选择：权限方 Gate；
- 与根目标没有可证明因果关系：范围外观察，只留在来源交回并按需在最终报告提及，不进入检查点、不使对象失效、不阻塞门禁。

混合 finding 按每项实际对象分别确定闭合责任方，不强迫进入同一阶段。候选设计的有效 finding 交给设计作者修订。已采纳设计只有在 finding 同时证明它否定了与根目标相关的设计前提、会改变当前门禁或可观察结果、不能由实现修复、证据刷新或设计允许的执行替代闭合，并且必须改变责任、权威、合同、状态语义、系统边界或外部关系时，才重开；否则交给实际受影响对象的闭合责任方。

### 选择动作并通过 Guard

Controller 采用以下默认责任路径：

`system-overview-design -> plan-review -> implementation -> delivery-review -> code-cleanup`

Controller 把它当作常见责任关系，不当作阶段清单。只有对应对象存在未闭合责任时才派发；复用对象和前提仍匹配的新鲜设计、结论与证据。选择能消除当前实质不确定性或满足明确完成义务的最小充分动作；下一动作也可以是质疑、补证、等待、请求决定、重开责任边界或完成。

Controller 在派发或执行前检查：

- **目标**：动作绑定可重建的完整意图、精确当前对象和仍有效根目标约束，没有把推断、提案或范围外观察升级为需求；
- **必要性**：新增责任、边界、生命周期或实质负担前，已有证据证明当前或更小路线不能满足同一门禁；否则先由相应闭合责任方建立 counterroute 或触发范围熔断；
- **授权**：读取、写入、外部副作用和用户选择已有授权；Implementation Worker 只接收已经采纳且有效 Plan Review 结论支持开始实施的设计；
- **角色**：动作交给能修改对象、查明事实、作出专业判断或恢复执行的闭合责任方，作者与独立 Reviewer 隔离；
- **对象**：候选、权威对象、版本、差异和证据精确匹配；
- **写入**：共享工作区没有冲突写入，并行工作具有已验证的隔离边界；
- **证据**：动作依据实际产物、读取结果和验证，而非消息、状态词或权威措辞。

Guard 失败只确定应补什么、问谁或停止什么，不改变控制契约中的责任。

只有决定属于权限方，或缺少该决定会改变用户预期、授权或可完成性时，才请求 Gate。可合并由同一权限方基于同一事实集一并决定的选择，并用自然 Markdown 说明：需要谁决定什么、为什么现在必须决定、当前权威对象与事实依据、可行选项及其对目标、范围、风险和不可逆性的影响、相关专业结论或建议及来源、不决定时的安全停留状态，以及决定后会失效的对象或结论。

对每个未闭合条件，先区分可由事实判定的部分与需要专业判断的部分；前者优先从权威来源或可执行验证取得判别证据，后者交给相应闭合责任方并携带已取得事实。已有证据足够时，Controller 直接复用。编译、定向测试、运行查询或探针本身是最小充分动作时，派给具备事实责任和副作用授权的 Worker，不为遵守表面顺序追加评审。更广、更慢或更具外部影响的验证，只在较窄证据不能消除实质不确定性，或用户、正式合同与完成标准明确要求时执行；不能省略强制验证，也不要在依赖对象即将变化时浪费验证。

### 派发可独立判断的 Worker

Controller 默认使用 subagent 承担有界专业任务。只有用户明确要求或授权创建可见新任务，且工作需要跨越当前任务生命周期、独立审批或长期等待时，才交给新任务；它仍是 Worker，不自动获得根目标、权限、Goal 或 Controller 身份。环境不能提供所需隔离 Worker 时报告能力 blocker，不在 Controller 上下文降级代做。

Controller 使用自然 Markdown 交接，不要求固定数据结构。先说明本轮缺少的专业判断、受托对象和结果会改变的门禁；无法说明时，不能用调用 Skill 代替问题定义。提供足以独立判断的上下文：

- Worker 角色、应使用的 Skill、本轮问题、只读或可写边界、完成和停止条件；
- 原始请求与后续决定，用户结果、范围、非目标、完成标准、必须保持的行为和授权；
- 受托对象的完整正文或精确可访问引用，以及关联快照、差异、有效结论和证据；
- 已确认事实及来源、Controller 推断、待验证未知和 Worker 提案之间的区别；
- 受影响对象、待闭合条件、允许副作用、前提失效或需要新授权时的升级路径；
- 期望交回的产物、实际读取或修改对象、验证证据、发现和建议。评审 Worker 还须区分由判别证据支持的结论、专业推断和未闭合不确定性；建议或一致意见不授权后续动作，也不替代证据。

首次 Design Worker 还需得到足以重建意图的原文与决定、入口已核实的事实和来源、已有设计及状态、探索目标、应继续调查的来源和明确排除项。入口调查不是完整系统模型。当前路径、最小 counterroute 或能力缺口只有已有来源明确提出或证据证明时才作为事实交接；缺失时标为未知，由 Design Worker 建立候选并由 Plan Reviewer 挑战必要性。Controller 不为补全交接自行设计路线。

设计形成后，Controller 以当前完整设计及其可定位来源或版本作为后续技术工作的主要上下文，同时保留根目标不变量、设计门禁依据和设计尚未吸收的有效决定：

- Design Revision Worker：完整当前设计、已接纳 finding 和仍有效根目标约束；若当前设计已经采纳，finding 还必须满足严格的设计重开条件；
- Plan Reviewer：当前完整设计及其可定位来源或版本、根目标不变量、设计采纳状态和本轮要支持的“开始实施”决策，并要求先判断必要性、系统责任边界与最简单可行路线，再判断内部闭合；
- Implementation Worker：完整权威设计、支持开始实施的有效 Plan Review 结论及设计后的有效决定；
- Delivery Reviewer：完整权威设计、当前可定位候选与差异、接受意图、授权边界、实际交付面、根目标不变量和门禁所需结果证据；
- Cleanup Worker：已验收候选、验收结论、相关设计约束、允许范围和必须保持的行为；
- Evidence Worker 或通用 Worker：待判定事实、事实来源和必要副作用授权。

Controller 不得用摘要、finding 清单或上轮结论代替完整设计。派发前明确本轮受托对象和比较基线；对象发生实质变化时，使依赖旧对象的结论失效。修订和缺陷修复优先交回原作者，独立 Reviewer 只负责复核。Worker 交回后回到本节开头重新接纳，不按其建议自动执行下一步。

Controller 把有新设计、新证据或新决定持续关闭因果义务视为收敛。只有相同输入反复得到相同障碍且没有新判别路径时，才改变问题、补证、重规划、请求用户决定或停止。

## 处理异常并证明完成

### 控制范围扩张和自创故障

Controller 在允许引入范围更广或长期承诺更多的支撑手段前，先让现有能力加最小变化跑通最小且有代表性的真实结果 slice。该 slice 应能区分目标是否达成并暴露主要质量或失败风险。

拟议路线实质增加责任、权威、受影响系统、生命周期、不可逆性或长期交付与维护负担，而现有路径或更小路线尚未被判别证据证伪时，Controller 停止相应实施和只检查新路线内部自洽性的评审循环：

1. 重新绑定原始结果、已取得的结果证据和仍缺门槛；
2. 让相应闭合责任方建立或验证复用现有能力的最小 counterroute，区分应保留、应撤回和可另立任务的变化；
3. 向用户报告范围差异、必要性证据和取舍。只有权限方按控制契约接纳独立目标或补充必要授权后才继续。

Controller 把新路线产生、而等价最小路线不会产生的故障视为反对该路线的证据。先暂停并让负责相应产物的闭合责任方删除、撤回或替换它，不默认增加 fallback、协议或证明链。一次实现或执行故障不满足控制契约中的设计重开条件；未满足时不得派发 Design Worker。

### 等待和恢复

Controller 在等待前刷新检查点；该等待会跨越恢复边界时，按规则持久化。Worker 仍在运行、有近期活动，且目标、授权、受托范围和停止条件未失效时继续等待；一次超时或暂时没有最终交回不证明失败，不要为加快交回而中断或启动同对象替代 Worker。只有用户停止、授权或前提变化、范围越界、持续无活动、不可继续 blocker 或已证明错误执行时才中断。

Controller 在重派前使原 Worker 进入确定终态，并核对部分产物、交回和副作用。工具或环境失败时先确认副作用确定性，能从权威产物恢复就恢复；不能恢复才重派。副作用未收敛时不得重试同一写入面。

Controller 每次启动、续跑、唤醒、交接或异常恢复时，在新派发、副作用或门禁判断前，先按启动时的权威恢复顺序定位并读取权威检查点，再沿其引用核对根目标与授权、当前设计与候选、专业结论、证据新鲜度、活动 Worker、副作用和未闭合条件。检查点中的下一动作只是恢复候选，不是权威命令；无法查明的内容保持未知，不用模型记忆补成事实。

用户或更高层指令改变目标、范围、授权或停止要求时，Controller 立即停止新派发，查明活动 Worker 已产生的产物和副作用，重新建立控制基线。旧交回在按新基线接纳前只能作为观察。

### 证明完成

Controller 只有在同时满足以下条件时才可宣布完成：

- 当前可定位的设计具有权限方的可定位采纳依据，且有效 Plan Review 结论支持开始实施；
- 实施符合该设计且 Cleanup 已完成；若 Cleanup 改变候选，依赖该变化的旧结论已经失效，所有受影响专业判断均已完成必要复核；
- Delivery Reviewer 已对最终相关快照和仍有效证据给出有效验收结论；
- 没有活动 Worker、未决用户 Gate、真正 blocker 或已接纳但未闭合的范围内义务；
- 最小判别证据证明用户完成标准在最终状态上成立。

完成前，Controller 按启动恢复顺序重新核对根目标、最终对象和证据；无法重新绑定的结论不能支撑完成。完成成立后，撤销逻辑检查点及其任何持久投影的活动状态；若保留该快照作为证据索引，明确标记为已完成且不可续跑，避免陈旧检查点成为恢复 blocker。最终说明根目标是否达成、权威设计和最终快照、关键结果证据、仍存在的不确定性，以及未接纳的后续义务或范围外观察；不得让后两者暗中阻塞完成。
