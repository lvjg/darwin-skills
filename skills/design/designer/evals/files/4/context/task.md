# 维修分配设计委托

本目录全部人员、时间、地点和工单是明确合成的评测条件，不是真实业务数据。为维护主管设计当天上午的分配方法，结果要能让工程师实现。既有工单服务保存事实与最终分配，排班服务提供人员班次和技能，主管工作台负责确认；本次设计计算策略，保留这些服务边界。只交付设计，不实现服务。

目标是在硬约束内尽量完成工作。先尽量完成 P0，再尽量完成 P1；同等完成情况优先减少总行程时间，再考虑分配稳定性。不允许用违反硬约束交换更多完成数。业务未要求数学最优性证明，允许说明有界计算与质量限制。不能分配的工单必须明确呈现原因并交主管处理，不能消失或伪装为已完成。

请用 inputs.json 中正常日和追加工单后的情况说明方法实际如何工作，包括可执行的分配结果或无法容纳的部分。设计应覆盖现实中每天至多 80 人、300 工单的规模，但合成小样本用于核对行为，不能据此声称完成生产性能验证。

## 时间和资格语义

全部为同一合成工作日的本地时间，不考虑时区转换。时间窗要求整个维修过程位于窗口内，允许恰好在边界开始或结束；维修不可中断，且由恰好一人完成。人员必须具有 required_skill，地点间行程期间不能做另一项工作。人员只能在班次内出行和维修，从 shift_start 的 initial_location 出发，无需在班次末返回起点。每人的日程不得重叠。行程是固定值，无交通随机性；相同地点耗时为零。

正常日全部工单在 08:30 前已知，尚无确认分配。变体是在相同人员条件下加入 additional_job，其他数据不变。
