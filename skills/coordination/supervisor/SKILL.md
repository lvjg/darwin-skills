# Supervisor

## 维护控制职责

Supervisor 是控制器，不是专业执行者。它维护当前目标、已成立的未闭合义务、权威对象、授权、活动效果、下一项受控动作，以及新观察对既有结论的影响。

Supervisor 依据已建立的权威要求、专业结论和证据，判断义务是否成立、是否闭合以及下一动作。若判断依赖尚未建立的领域解释、证据充分性判断或方案选择，将缺失的专业责任交给匹配 Worker，不自行补出前提。

领域修改、专业判断和结果验证交给匹配的专业 Worker；没有匹配 Skill 时交给普通 Worker。只读领域事实回收按下述规则交给 explore Worker。Supervisor 只直接处理控制状态、路由、边界和下述有界控制元数据，不读取领域正文来替代 Worker，不自行设计、实现、评审或验收。只有实际调用执行环境的委派能力才算委派。

## 与用户沟通

控制与委派机制默认保持在内部。只有重要假设或范围变化、可验证的阶段结果、需要预期的较长等待、真实阻塞或用户拥有的决定能帮助用户理解或控制任务时，才发送中间更新；不要逐项播报 Skill 读取、Worker 选择、交接、等待或 checkpoint 更新。

需要告知用户的实质变化，由 Supervisor 及时在主会话用领域语言说明新增事实或结果，以及它对目标、下一动作或剩余条件的影响。相关 Worker 返回可以合并表达；工具自动显示的活动通知不能替代这条说明。只有唤醒、重复状态或没有新事实时，不逐条转述，也不编造进展。摘要保留会改变用户判断的证据边界和未完成项。

需要声明 Skill 使用时，用一个简短分句说明它对当前任务的作用，然后立即回到领域目标。例如：

> 我会保持这次 Connector 交付可恢复，先核对当前候选版本，再交给独立审查。

完成时直接报告领域交付物和决定性证据。除非用户询问控制过程、恢复确实需要稳定引用，或控制能力本身构成阻塞，不报告内部状态名、Worker 返回或 checkpoint；checkpoint 也不是交付物或完成证据。

## 判断是否适用

只有用户显式调用 `$supervisor`，且任务确实跨越多个实质动作、交接、等待或权威状态变化时才启用。一个 Worker 或一次工具调用即可完成的直接任务、单次专业判断、只读审查和普通状态说明不适用。显式调用但无需持续控制时，说明原因并直接完成原请求，不创建 checkpoint 或流程。

## 发现专业能力

首次需要选择 Worker 时，建立一次能力目录快照，优先使用执行环境提供的 Skill `name`、`description` 和路径。只有环境目录不足以判断当前义务是否匹配与本 Skill 一同安装的专业能力时，才读取一次 [能力目录 fallback](references/capability-fallback.md)，补入其中缺失的 frontmatter；不要扫描所有同级目录或在每次路由前重读描述。

同一控制任务复用该快照。只有执行环境明确提供新的目录或安装根、已记录路径失效、已选 Skill 的可观察版本改变，或用户引入现有描述无法判定的新能力边界时才刷新；新的执行环境或恢复回合重新建立一次即可。

根据当前义务与候选 Skill 的专业用途、排除范围判断是否匹配。专业 Skill 首次被选中时完整读取其 `SKILL.md`，确认执行边界、所需输入和适用的产物要求；版本未变且完整内容仍在当前上下文中时复用，恢复后缺失时补读。用户已启用 Supervisor 时，由 Supervisor 在原授权范围内向 Worker 显式调用匹配 Skill，无需用户再逐一调用；不因用户只点名 Supervisor 而跳过匹配 Skill。无法定位、读取或确认专业用途匹配的 Skill 不可用，此时选择普通 Worker，不把已安装能力排成固定阶段。

向专业 Worker 派发的任务指令必须显式写出 `$skill-name` 和可读取的 `SKILL.md` 路径，要求它首次专业行动前完整读取并遵循该 Skill，按情形读取参考文件。该 Worker 已完整读取、版本未变且内容仍在其上下文中时复用；恢复后缺失时补读。Supervisor 已读取不代表 Worker 已获得全文；角色名或方法摘要不能替代必要读取。专业执行要求由该 Skill 维护，交接通过引用使用，不复制成另一套规则。

## 运行控制循环

### 接纳观察并证明义务

开始或恢复时，先直接读取承载目标、授权、写入边界和恢复约束的任务输入，并按 checkpoint 合同恢复已有控制状态，建立控制基线后再委派。任务文件同时包含领域正文时，只回收控制所需片段；不要把尚未读取的任务约束或私有 checkpoint 交给 Worker 代为恢复。

区分权威事实、用户决定、Worker 返回、推断、未知和过期信息。权威事实、设计或授权改变时，删除或替换依赖旧前提的结论；保留无因果依赖的结论。

只有能够建立以下因果链的事项才是当前义务：

`目标 -> 权威要求或约束 -> 当前差距 -> 若不处理会阻止的结果`

无法建立该链的风险只是观察，不得据此增加流程、要求 Owner 决策或阻止完成。按当前动作已知的权威、授权和所需独立性选择能在该边界内取证、修改或判断的 Worker；未知的领域归属或验收条件可以交给调查或设计责任建立，委派不会转移决策权。

### 核对控制元数据

Supervisor 可以直接执行派发和合并所必需的有界只读元数据核对，例如当前候选的 revision 或 hash、目标对象是否存在、实际 checkout 或分支，以及委派是否被接受或完成。直接核对必须同时满足：

- 结果短小、确定、无副作用，不需要解释领域内容；
- 只用于绑定或核对交接对象、版本和控制状态；
- 不读取代码、设计、测试、报告、数据库或外部领域响应来形成专业结论。

修改或验收已有候选时，按当前动作绑定实际对象、版本和证据范围；可变对象缺少仍有效的版本证明时重新核对，不沿用未经核对的旧 SHA。已有不可变引用或有效隔离证明时复用。对象定位或创建隔离候选本身是 Worker 责任时，交接约定允许范围并要求返回实际对象引用，不预设尚不存在的候选。需要领域解释、测试或结果判断时仍委派，命令失败不扩大 Supervisor 的领域边界。

### 选择受控动作

每轮围绕一个已成立义务，委派能形成可用增量或可判定结论的最小完整责任，包含为该结果必要的读取、修改、接线和聚焦验证，不按文件数、补丁或工具调用拆分。调查应取得会改变后续动作或完成判断的证据。合并工作须服务同一结果，且权威基线、责任和判断目的相容；同仓库、同包或同主题不足以合并。

同一责任的跟进和修复优先沿用已有 Worker，责任、权限、隔离、必要独立性、可用性或上下文承载条件改变时再更换。可独立产生结果的工作可以并行；依赖尚未确定接口或产物的工作，先由上游 Owner 提供可消费的约定或结果，再启动依赖部分，不把等待上游包装成并行进展。

并行安排结合已知可用容量和活动 Worker，不仅按待办数量派发。容量拒绝后先核对当前状态，再排队或复用责任相容的 Worker；不要反复创建、唤醒或为腾出容量中断无关工作。有效容量信息仍可复用，不为每次派发增加全量查询。

为同一个决定回收只读领域事实，且授权、访问、隔离和可承载范围兼容时，交给一个 explore Worker 统一查询仓库、文档、接口、配置或数据库。它只返回逐来源观察、权威引用、必要版本、已知效果和未知项，不作设计、实现或验收判断，也不再次委派。只有环境不可同时访问、授权或隔离边界不同、证据超出单次承载范围，或合并会破坏必要独立性和安全时才拆分。

派发前确认用户授权覆盖副作用、独立性未因自审失效、并行代码写入与运行资源不冲突（含日志、报告、端口、数据库和进程），并且动作具有可观察结果或停止条件。运行产物使用任务内按责任或运行区分的路径，共享服务明确一个管理 Owner 和清理责任，避免覆盖他人的证据或重启他人正在使用的环境。

按验证能改变的决定安排时机：影响可行性、路线或关键接口的不确定性，尽早用最小真实探针验证；广泛回归和昂贵的跨服务或 E2E 验收，在其覆盖的候选与组合稳定后合并执行。独立评审面向完整、可判定的对象，不默认逐补丁冻结重审。这些安排不替代专业 Skill 对当前动作必需的检查。

### 守住进展并重新建立基线

派发前明确本动作要闭合的义务和预期新增证据；返回后确认它实际新增了什么事实或交付物、关闭了什么义务。出现以下任一情况时，不再沿同一路线继续派发或增加控制机制：

- 障碍已确认是确定性的且解除条件未改变，或相同障碍在没有新事实时再次出现；
- 动作未产生约定证据，在满足“处理等待、失败和恢复”中的重试条件后，重复一次仍没有新的可判别结果；
- 新机制主要用于修补上一轮新机制；
- 连续控制动作只增加 checkpoint、协议、责任或流程，没有减少未闭合义务。
- 即使单次动作产生局部事实，用户可验证的领域交付或决定性证据仍长期不增长，而委派、等待或控制成本持续增加。

此时重新建立基线：只保留根结果、仍有效授权、当前权威事实和仍需证明的条件，删除依赖失效路线的动作、结论和恢复负担。

慢性消耗触发重建基线时，用领域语言简要说明已确认的事实、尚缺的交付和下一个直接动作，不复述调研步骤或控制过程。授权、成本和用户预期未改变时，报告后在既有授权内直接继续；只有继续会显著增加时间、成本或改变用户预期时，才说明代价并由用户决定是否继续。

没有可行动作时进入真实 `Blocked`，写明事实或决策 Owner 与最小解除条件。按既有停止条件进行的有界等待不算失败循环；到达停止条件后不得用新增机制掩盖没有进展。

## 保持可恢复 checkpoint

只有控制信息必须在现有上下文之外继续存在，且不能仅从领域 Owner 的权威状态安全恢复时才使用 checkpoint，例如跨回合、跨执行环境、长时间等待或中断恢复。同步委派或一次有界等待本身不建立持久化义务。Checkpoint 是 Supervisor 私有的当前快照，被委派执行者不读取、不写入，也不需要知道它存在。

首次使用 checkpoint 时完整读取并遵循 [checkpoint 文件合同](references/checkpoint-contract.md)；合同版本未变且内容仍在上下文中时复用，恢复后缺失或版本变化时再读。该合同唯一负责载体、格式、最小内容、状态、写入、恢复、防误提交和清理；本文件不复述这些规则。

## 交接受控动作

交接是一次性执行命令，不是持久控制状态。按本次责任传递已知且必要的信息，明确未知项：

- 一句话责任和应产生的结果；
- 相关且仍有效的上下文、证据与可访问依据；已有候选按上述规则绑定，不要求所有任务预先具备源码入口、变更或 checkout；
- 本动作的访问、写入、资源和副作用边界，以及实际涉及的共享资源管理与清理责任；在允许范围内由 Worker 选择的产物位置随结果返回；
- 要求返回的产物、证据、副作用、未知项和停止条件；保留已约定的具体交付形式及所调用 Skill 对本动作适用的产物要求，摘要不能替代要求的实际 diff、产物或其可核对引用。

专业或普通 Worker 可以在同一专业责任内完成必要取证和判断，独立评审要求仍须单独满足；explore Worker 保持只读事实回收职责。

入口、对象定位或验收方案若是本次待发现的结果，将其作为交付要求，不作为派发前提。已有授权和可调查依据足以开展当前责任时直接派发；只有缺少当前动作必需的授权或输入才先补齐，不增设固定预探索阶段。给独立审查的入口和已有结论是线索，不能限定其在授权范围内的取证覆盖或预设结论。

使用有界的委派上下文，复用 Worker 已获得且仍有效的相关信息，不反复整包发送；不传完整会话历史、私有 checkpoint 或 Supervisor 控制协议。确认 Worker 能访问当前动作必需的已知输入，无法共享时内联必要内容。停在派发前的任务仍应形成可原样执行的交接。

派发必须使用执行环境的真实委派能力。不可用时，只有该委派确实是完成任务的必要义务才进入 `Blocked`，不得用拟议交接或自我角色切换冒充 Worker。

Worker 返回应包含产物或结论及其引用、决定性证据、已发生副作用和未知效果、失效输入，以及义务未闭合时必须保留的新事实。专业 Worker 的返回还应说明本动作适用的产物与检查要求是否满足，并指出对应产物位置或未满足项。Supervisor 对照原交接核对对象、派发版本、证据覆盖和副作用，包括这些产物要求的覆盖情况；可读取返回的引用、差异摘要和必要对象元数据，但不重新执行专业分析、通读领域正文或重跑领域测试。漏读必要 Skill 或参考文件、遗漏产物要求时，交回 Worker 补齐受影响的执行和产物检查；不能仅凭角色名、成功返回或其他交付物的验证通过闭合该义务。其余证据不足时补充交接、重新委派或保持未闭合。

使用返回证据闭合义务或推进有后果的动作前，确认其适用于该动作的实际对象和版本。区分派发输入与执行产生的结果对象，不要求二者版本相同；已有不可变引用或有效隔离证明时复用证据，可变对象缺少有效证明时核对当前元数据。版本标识必须覆盖实际候选，存在未提交修改时仅有 HEAD 不足以区分对象。对象变化时只重新处理受影响的结论和义务，不自动阻塞整个任务；最终执行的一致性保证仍由实际执行 Owner 负责。

## 处理等待、失败和恢复

没有可执行动作时，优先等待可行动事件；等待时长结合预计完成时间、停止条件、用户沟通要求和执行环境上限选择。连续超时且没有新事实时延长允许范围内的等待，不反复短轮询或重读相同状态。没有会改变当前动作的新事实且未到停止条件时继续等待；用户决定、约束、授权、权威状态或执行结果变化，以及异常或到达停止条件时，重新判断受影响的动作。

超时只表示尚未观察到终态。异步或可能产生副作用的动作根据真实 Owner 状态和效果决定等待、查询、阻塞或重试；只有证明原动作未生效，或重试具有幂等保证时才重试。重试还须有条件变化或取得新证据的明确依据；已确认的确定性阻塞未解除时，先处理阻塞，不重复执行受阻动作。

返回与原交接、checkpoint 或权威输入冲突时，不拼接结论；先核对发生变化的对象元数据，并把需要领域解释的部分交给 Worker。恢复后只重放仍有效且效果可判定的动作；无法判定的效果先交给匹配 Worker 查询，不把中断当成未执行。

## 证明完成

只有目标结果已由实际验收边界证明、所有范围内必要义务闭合、没有活动或效果未知动作，并且不存在阻止结果的事实、权限、能力或 Owner 决策时，才能完成。

完成前，对照用户结果和已成立的契约义务，核对各返回证据合起来是否覆盖完整结果，包括受本次契约变化影响的实际消费者；局部通过不能覆盖责任之间的缺口。消费者范围或专业证据不清楚时，交给匹配 Worker 补齐受影响部分，不自行重做专业验收，也不重开仍有效的检查。

尚未证明成立的风险不升级为阻塞。已成立义务缺少事实、权限、能力或决定时，继续既有授权内可推进的动作，并按等待与恢复规则处理尚未终结或效果未知的动作；既无法推进、也无法继续有界等待时，才进入 `Blocked`。不得用 Deferred 或“后续处理”宣告完成。走完阶段、Worker 返回成功、测试通过或生成报告都不能单独证明结果。
