# Darwin

> 让复杂任务从意图出发，以责任和精确对象为边界，以可验证证据闭环。

Darwin 是一组面向 Codex 的系统级工程 Skills。它们不追求增加流程，而是解决复杂工作中最容易断裂的关系：用户真正要的结果、当前权威事实、权限与责任、被采纳的设计、实际候选、独立专业判断，以及最终可以证明的结果。

`Darwin` 是产品名；本仓库使用 `darwin-skills` 作为源码与分发 slug。各 Skill 以自身稳定责任命名，不继承仓库名作为调用前缀。

七个专业 Skill 各自承担一个可独立使用的判断、验收或收敛责任；`supervisor` 是与领域正交的长程控制能力，只在任务需要跨多个物质动作、交接、等待或权威状态变化保持一致时进入。Controller 不包含专业 Skill，也不规定调用顺序。

## 为什么需要 Darwin

复杂任务真正困难的地方，通常不是缺少生成方案或代码的能力，而是工作跨越多个角色、对象和回合后，原始意图、权威事实、决定与授权、专业判断和完成证据逐渐失去一致性。Darwin 将长程推进视为一个持续缩小结果差距的控制问题，同时把系统设计、方案评审、代码验收、行为验收、E2E、产品走查和实现收敛保持为彼此独立的专业责任。

| 要解决的痛点 | 整体思路 |
| --- | --- |
| 用户想要的结果在设计和实施过程中逐渐漂移 | 把原始结果、范围、授权和完成标准作为稳定根基；后续方案、动作与判断都必须说明它们如何缩小当前结果差距。 |
| 已经明确授权的动作被反复确认，尚未授权的阶段变化却被自动推进 | 区分可调查事实、权限方决定、动作授权和平台审批；验证已有授权是否语义覆盖当前动作，只在实际权限方的决定仍未解决或覆盖因新事实失效时询问。 |
| 设计、代码实现、行为交付、评审和测试讨论的不是同一个对象 | 为设计、代码候选、有效行为组合和证据绑定精确来源与版本；对象变化时只保留仍然有效的结论，并重新判断受影响部分。 |
| 专业作者、修改者和判断者相互替代，责任和结论失真 | 专业 Skill 只拥有自己的产物或判断；Controller 绑定目标、对象、Owner 和证据，但不代签事实、设计、评审、验收或权限决定。 |
| 固定流程关注“进行到哪一步”，却不能回答“现在最该解决什么” | 每轮从新观察中定位会改变下一决策或完成判断的关键缺口，确认实际 Owner、能力和授权，选择一个能够产生判别证据的动作，通过 Guard 后重新观察。 |
| 测试通过、PR 合并或状态完成被误当成最终结果 | 完成判断回到用户可观察结果：最终对象、有效专业结论和结果证据必须相互绑定，且范围内义务、活动副作用和真实 blocker 已经闭合。 |
| 功能 E2E 与产品体验走查混在一起，既无法准确证明系统结果，也容易把审美意见变成 blocker | E2E 从结果义务和反例推导最小 case，并用真实入口、权威终态和副作用证明功能旅程；产品走查独立沿真实用户任务发现内容、层级、布局、交互、反馈和恢复问题。 |
| 连续修补不断引入兼容、恢复和中间状态，系统没有真正收敛 | 当动作不再缩小原始缺口或责任面持续扩大时停止补丁并重新建立基线；结果确认后删除重复和过时路径，收敛为唯一维护路径。 |

## 工作机制

各 Skill 可以独立使用，不存在设计、评审、实施、验收和清理的默认流水线。所有 Skill 都需要用户显式调用；调用 `supervisor` 不会自动加载或调度专业 Skill，专业 Skill 之间的引用也只是后续调用建议。`supervisor` 通过可恢复检查点维护根结果、授权覆盖、权威对象、未闭合义务、证据、活动动作和恢复条件；每轮按当前关键缺口动态寻找事实来源、对象 Owner、专业判断者、结果验证者或权限方。新增一种专业能力不需要修改 Controller。

## Skills

根控制器使用 `supervisor`；其他 Skill 直接以稳定角色命名，不再依赖家族前缀表达归属。

| Skill | 设计意图 | 关键机制 |
| --- | --- | --- |
| [`supervisor`](skills/supervisor/SKILL.md) | 在跨动作、交接、等待和状态变化的任务中维持可恢复控制，而不把专业能力组织成固定流程。 | 维护根结果、决定与授权依据、权威对象、义务、证据失效关系和活动动作；每轮动态发现实际 Owner，选择一个受 Guard 约束的因果动作，并处理等待、未知副作用、恢复和重新基线。 |
| [`overview-designer`](skills/overview-designer/SKILL.md) | 设计首先是一项系统判断，其次才是文档表达；目标是形成有证据支持的最小完整设计，而不是补齐模板或堆叠架构元素。 | 从可观察结果和真实约束建立问题，比较可行路线与最强简单替代，明确责任、合同、状态、失败和演进语义，再用关键场景挑战并收敛设计。 |
| [`design-reviewer`](skills/design-reviewer/SKILL.md) | 评审设计路线本身，而不是润色方案文档或提前验收代码。 | 独立重建问题与适用起点条件，存在现有系统时检查其相关模型，并检查能力选择、责任与权威、合同与状态、失败语义、长期结构和迁移可执行性，区分已成立缺陷、决策性未知和用户选择。 |
| [`code-reviewer`](skills/code-reviewer/SKILL.md) | 验收精确代码候选，而不是根据 diff 大小、测试数量、已批准设计或实现者声明判断完成。 | 重建要求与实际代码交付，从真实消费者和选中路径检查实现、接线、合同、状态、依赖、失败语义、迁移、运维和代码证据；不代替实际行为验收。 |
| [`behavior-reviewer`](skills/behavior-reviewer/SKILL.md) | 验收由 instructions、agent/model、workflow、工具路径或 presentation channel 共同决定的精确行为候选。 | 绑定实际加载的运行组合，沿事实、权限、指令优先级、判断、动作、权威结果和最终呈现追踪行为，用对照场景和适配证据区分行为缺陷、代码边界与验证未知。 |
| [`code-simplifier`](skills/code-simplifier/SKILL.md) | 在目标结果和保留行为已决定或接受后，让现有实现收敛为唯一、可维护的实现，而不是进行风格优化或无边界重构。 | 重建受影响的关键执行路径，对每个机制做必要性判断，优先删除和复用，关闭旧入口、旧路径及其再生产机制，并从行为保持、旧路径退出和净简化三个维度证明结果。 |
| [`e2e-verifier`](skills/e2e-verifier/SKILL.md) | 证明具体产品或系统旅程的功能结果，而不是把低层测试、页面体验或模拟路径当成端到端通过。 | 先固定精确验收候选和环境，再从物质义务与反例形成最小 case 集，按证明责任选择真实入口和能力，以可见结果与权威事实组成双重 Oracle，并通过用例质量、执行闭合和接受边界真实性三个门禁区分产品、Verifier、脚手架与环境问题。 |
| [`ux-reviewer`](skills/ux-reviewer/SKILL.md) | 从目标用户完成真实任务的过程发现产品体验问题，而不是证明后台或系统功能正确。 | 沿代表性人机路径检查内容、信息层级、导航、动作、反馈、布局、可达性和恢复，用真实 witness 将发现区分为阻断缺陷、实质缺陷、风险、偏好和非体验功能偏差。 |

## 什么时候使用

- 创建、补全或重写系统级设计产物：`$overview-designer`
- 对拟议技术或行为路线做独立、只读决策：`$design-reviewer`
- 对精确代码候选的实现、接线、合同、状态、迁移和代码证据做独立、只读验收：`$code-reviewer`
- 对精确的指令、agent/model、workflow、工具路径或渠道行为组合做独立、只读验收：`$behavior-reviewer`
- 在目标结果和保留行为已决定或接受后收敛现有实现：`$code-simplifier`
- 规划或执行具体功能旅程的 E2E 验收：`$e2e-verifier`
- 沿真实用户任务走查内容、布局、交互、反馈和恢复体验：`$ux-reviewer`
- 控制或恢复跨多个物质动作、交接、等待或状态变化的长程任务：`$supervisor`

## 安装

使用 [Agent Skills CLI](https://github.com/vercel-labs/skills)，需要 Node.js 18 或更高版本。

查看仓库中的 Skills：

```sh
npx skills add lvjg/darwin-skills --list
```

将全部 Skills 全局安装给 Codex：

```sh
npx skills add lvjg/darwin-skills --skill '*' --global --agent codex --yes
```

只安装一个 Skill：

```sh
npx skills add lvjg/darwin-skills --skill design-reviewer --global --agent codex --yes
```

如需项目级安装，去掉 `--global`。

## 更新

已安装当前名称的版本时，可以直接更新：

```sh
npx skills update --global --yes
```

`skills update` 不会把已经删除或拆分的 Skill 名称自动迁移为新名称。从 v0.1.0 升级时，先按 [MIGRATIONS.md](MIGRATIONS.md) 安装新全集并核对映射，再删除旧名称。

## 分发边界

本仓库当前是通过 Agent Skills CLI 安装的社区 Skill 源，不是 Codex 或 ChatGPT Plugin。安装命令只分发 `skills/` 中的 Skill；若目标变成 Plugin 分发，需要另行建立 manifest、依赖与发布路径，并按该入口验证安装和发现，不能把这里的 CLI 安装结果视为 Plugin 发布证明。

## 发布检查

提交前运行非 eval 的仓库打包检查；它验证 Skill frontmatter、目录名、`agents/openai.yaml`、显式调用策略、本地链接、README 清单、重命名迁移记录和 diff 格式：

```sh
ruby scripts/check-packaging.rb --base HEAD
```

Pull Request 和 `main` 分支上的相同检查由 [Packaging workflow](.github/workflows/packaging.yml) 执行。

## 全局工程原则

[`codex/AGENTS.md`](codex/AGENTS.md) 是独立的 Codex 全局工程原则模板，不是 Skill，也不会由 Agent Skills CLI 安装。使用前应先审阅其内容，再决定是否作为全局 `AGENTS.md`。
